# 仓库结构与边界

## 分层原则

仓库按“可独立构建和部署的应用”“跨应用契约”“内容生产流水线”划分，而不是把所有文件按扩展名堆放。

- `client/` 和 `server/` 是两个独立应用，各自拥有代码、测试和构建边界。
- `shared/` 只定义跨端契约，不承载业务实现。
- `game-data/` 是结构化玩法配置的生产流水线。
- `tools/` 服务于整个仓库，不参与游戏运行。
- `art-source/` 保存正式美术制作源文件，`client/assets/` 保存其运行时导出物。

## 领域模块

客户端和服务端使用一致的业务词汇：

| 领域 | 职责 |
|---|---|
| `auth` | 登录、会话和身份认证 |
| `users` | 玩家档案、货币、等级和基础状态 |
| `cards` | 卡牌定义、库存和卡牌操作 |
| `collection` | 套卡进度、集齐提交和奖励 |
| `crafting` | 配方、卡炉槽位、炼制计时和领取 |
| `market` | 交换、交易和市场订单 |
| `missions` | 新手、成长和日常任务 |
| `social` | 好友互动、消息、动态和偷炉 |

初期服务端采用模块化单体。模块拥有自己的业务规则和持久化边界；禁止为了方便而跨模块直接读写数据库表。

## 客户端资源与数据的区别

- `client/assets/` 是图片、动画、音频、字体和 Shader 等二进制或视觉资源。
- `client/resources/` 是 Godot `.tres`、`.res` 等引擎资源定义。
- `game-data/` 是卡牌属性、配方、概率、奖励和任务等可校验的结构化配置。

卡牌图片属于 `client/assets/art/cards/`，卡牌数值属于 `game-data/`，两者通过稳定的卡牌 ID 关联。

## 参考资料隔离

仓库根部的 `代号童话（策划资料）/` 仅用于研究和设计参考。正式代码、资源或配置不得通过相对路径读取该目录，以确保删除参考资料后游戏仍能完整构建和运行。
