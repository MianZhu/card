# 房间模板制作规范

> 状态：阶段 1 规范
> 更新日期：2026-09-01
> 依赖：[程序化关卡生成技术方案](PROCEDURAL_LEVEL_DESIGN.md)

## 1. 房间模板是什么

房间是一个由策划手工制作的完整地图块，可以占用一个或多个逻辑大格。一个大格固定包含 `16×16` 个 TileMap 小格。

房间模板负责：

- 地面、墙体、碰撞和建筑；
- 装饰与遮挡；
- 房间外轮廓上的连接接口；
- 宝箱、散落物、怪物、出生和撤离候选点；
- 房间内巡逻点和允许跨房巡逻的接口网关。

房间模板不负责：

- 选择自己连接哪个房间；
- 决定本局实际生成多少宝箱或怪物；
- 生成玩家、HUD、相机和完整关卡逻辑；
- 在运行时自行移动或旋转。

## 2. 标准节点结构

```text
RoomRoot                       RoomTemplate
├── Ground                    TileMapLayer
├── Structures                TileMapLayer / Node2D
├── Boundary                  StaticBody2D
├── Ports                     Node2D
│   ├── PortNorth             RoomPort
│   └── PortEast              RoomPort
├── ChestSpawnPoints          Node2D
├── LooseLootSpawnPoints      Node2D
├── EnemySpawnPoints          Node2D
├── PatrolPoints              Node2D
├── PlayerSpawnPoints         Node2D
├── ExtractionPoints          Node2D
└── Decorations               Node2D
```

阶段 1 验证器只强制要求根节点挂载 `RoomTemplate`，并存在名为 `Ports` 的直接子节点。其他容器可随对应系统实现逐步加入。

模板中禁止放置：

- `Hero` 或其他玩家实例；
- `Camera2D`；
- HUD、背包 UI、GameOverUI；
- `mian.gd` 等完整关卡脚本；
- 每个房间独立的场景切换逻辑。

## 3. 理解小格、大格和锚定大格

### 3.1 小格

小格是 TileMap 中编号为 `(x,y)` 的基础菱形格。它显示为菱形，但坐标仍是逻辑直角坐标。

### 3.2 大格

每个大格包含：

```text
16×16 个小格
```

大格 `(bx,by)` 对应的小格起点为：

```text
(bx×16, by×16)
```

### 3.3 锚定大格

每个房间从实际占用的大格中选择一个作为锚定大格，并把它定义为房间局部大格 `(0,0)`。

锚定大格：

- 不是房间贴图中心；
- 不是菱形最上方或最左方顶点；
- 不要求位于房间几何中心；
- 只是房间放到关卡大格坐标时的统一基准。

建议选择靠近房间结构中心、容易理解的占用格作为锚定大格。

## 4. 房间占用形状

### 4.1 单格房

```text
[0,0]
```

```gdscript
occupied_blocks = [Vector2i(0, 0)]
```

### 4.2 T 形房

```text
[-1,0] [0,0] [1,0]
          [0,1]
```

```gdscript
occupied_blocks = [
	Vector2i(-1, 0),
	Vector2i(0, 0),
	Vector2i(1, 0),
	Vector2i(0, 1),
]
```

对应小格范围：

```text
左格：x=-16..-1，y=0..15
锚定格：x=0..15，y=0..15
右格：x=16..31，y=0..15
下格：x=0..15，y=16..31
```

TileMap 支持负格坐标，可以正常在左格区域绘制。

### 4.3 L 形房

```text
[0,0]
[0,1] [1,1]
```

```gdscript
occupied_blocks = [
	Vector2i(0, 0),
	Vector2i(0, 1),
	Vector2i(1, 1),
]
```

### 4.4 占用形状原则

- `(0,0)` 必须包含在 `occupied_blocks` 中；
- 同一个大格不能重复填写；
- 地面、碰撞和可交互建筑不得进入未声明的大格；
- 树冠、屋顶等纯视觉元素可以越出，但不得破坏相邻房间可读性；
- 房间之间是否重叠只按 `occupied_blocks` 判断，不按屏幕 AABB 判断。

## 5. 房间接口

### 5.1 接口不是门

接口只是房间外轮廓上的标准连接开口。连接成功后可以：

- 保持开放通道；
- 生成普通门；
- 生成特殊门。

未连接接口必须封闭。门的美术和最终宽度不属于房间布局算法。

### 5.2 添加接口

在 `Ports` 节点下添加 `Marker2D`，挂载 `RoomPort` 脚本，并配置：

```text
block         接口所在局部大格
方向          NORTH/EAST/SOUTH/WEST
profile       首版使用 normal
edge_start    沿边界开始位置
edge_length   开口占用格数
allow_door    是否允许生成门
```

### 5.3 外轮廓规则

接口必须朝向房间外部。

T 形房间中，`(0,0)` 的南边邻接 `(0,1)`，因此这条边属于房间内部，不能放外部接口。

判断规则：

```gdscript
var outside_block := port.block + port.direction_vector()
```

如果 `outside_block` 仍在 `occupied_blocks` 中，该接口就是非法的内部接口。

### 5.4 开口范围

`edge_start` 从 `0` 开始计数，`edge_length` 必须大于 `0`，并满足：

```text
edge_start + edge_length <= 16
```

同一大格同一外边上的两个接口不能占用重叠的小格范围。

普通接口宽度尚待灰盒测试。测试完成前，所有正式模板必须使用同一套临时 `normal` 参数，不能每个房间自行决定。

### 5.5 接口净空

每个接口内侧必须保留无固定阻挡区域。这里禁止放置：

- 固定建筑；
- 宝箱和散落物生成点；
- 怪物生成点；
- 出生或撤离点；
- 无法破坏的大型装饰。

后续编辑器工具会把净空区域可视化；当前阶段由制作人手工检查。

## 6. 候选生成点

房间内摆放的是候选点，不代表每局全部启用。

### 6.1 宝箱点

建议记录：

- 允许品质；
- 权重；
- 是否保底；
- 最低难度；
- 交互方向和净空要求。

### 6.2 散落物点

建议数量大于实际生成数量，并避免：

- 接口净空区；
- 固定碰撞内部；
- 出生点正下方；
- 玩家无法到达的装饰区域。

### 6.3 怪物点

建议记录：

- 允许的怪物标签和体型；
- 威胁范围；
- 巡逻模式；
- 房间内路线或巡逻网关；
- 距离出生点的限制。

### 6.4 出生点与撤离点

- 只有出生类模板需要玩家出生候选点；
- 只有撤离类模板需要撤离候选点；
- 必须留出玩家和多人队伍的安全空间；
- 不得紧贴接口、固定障碍或怪物生成点。

## 7. 巡逻点与跨房网关

房间内巡逻路线由策划手工设计。建议节点结构：

```text
PatrolPoints
├── RouteA_Point01
├── RouteA_Point02
└── RouteA_Point03
```

允许怪物跨房间通过的接口，需要在接口内侧设置巡逻网关。关卡生成完成后：

- 已连接接口两侧网关互相连接；
- 未连接接口不加入巡逻网络；
- 禁止怪物通过的接口不建立怪物导航连接。

模板不应写死“去 room_5”，只描述怪物可在本房、相邻房或一定图距离内巡逻。

## 8. 碰撞与导航

- `CollisionShape2D`、`CollisionPolygon2D` 必须属于有效的 `StaticBody2D`、`Area2D` 或物理节点，不能直接挂在普通 `Node2D` 下期待产生碰撞；
- 已连接接口不得残留封口碰撞；
- 未连接接口必须有封口碰撞；
- 房间内部正式接口必须能到达主要可行走区域；
- 怪物导航区域需在允许通过的接口处对齐，后续可用 `NavigationLink2D` 显式连接。

## 9. 制作步骤

1. 新建标准 `RoomRoot`，挂载 `RoomTemplate`。
2. 创建 `Ground` 和 `Ports` 等标准容器。
3. 选择一个实际占用的大格作为锚定大格 `(0,0)`。
4. 填写 `occupied_blocks`，包含 `(0,0)`。
5. 按每 16 小格一个大格绘制手工地形。
6. 只在占用形状外轮廓添加 `RoomPort`。
7. 使用统一的临时 `normal` 接口规格。
8. 为接口保留无障碍空间。
9. 摆放宝箱、散落物、怪物、出生和撤离候选点。
10. 摆放房间内巡逻点和必要的接口网关。
11. 配置房间类别、权重、深度和实例上限。
12. 运行房间验证器，修复全部错误。
13. 在灰盒关卡中验证玩家和怪物实际通行。

## 10. 发布前验证清单

### 数据

- [ ] `room_id` 唯一且稳定；
- [ ] `(0,0)` 在 `occupied_blocks` 中；
- [ ] 没有重复占用大格；
- [ ] 所有接口所属大格都存在；
- [ ] 所有接口都朝向外轮廓；
- [ ] 接口范围合法且互不重叠。

### 场景

- [ ] 没有玩家、相机、HUD 或完整关卡脚本；
- [ ] 地面和碰撞没有进入未声明大格；
- [ ] 碰撞节点拥有正确物理父节点；
- [ ] 接口净空区没有固定阻挡；
- [ ] 生成点位于合法可达区域。

### 通行

- [ ] 玩家可从内部区域到达全部接口；
- [ ] 接口拼接后地面无缝；
- [ ] 封口关闭时不能走出地图；
- [ ] 允许通过的怪物能够穿过接口；
- [ ] 不允许通过的怪物不会选择该接口。

## 11. 现有 room_0~8 的迁移说明

现有模板仍是从完整关卡复制出的半成品，包含玩家或关卡级节点，且缺少标准接口和占用数据。不要批量文本重写这些大型 `.tscn`。

后续流程：

1. 先创建一个全新的标准灰盒房间；
2. 验证锚定大格、接口和拼接规则；
3. 再在 Godot 编辑器中逐个迁移旧房间；
4. 每迁移一个就运行验证和灰盒通行测试；
5. 不在迁移过程中顺带重构无关系统。
